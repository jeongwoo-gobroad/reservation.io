# rev_003 예약 피크 완충 구조

이 문서는 다음 구조를 실제 서비스에 적용하기 위한 변경 명세입니다.

```text
Vercel Redis waiting room
→ 입장 허용된 사용자만 Cloud Run 예약 변경 요청 API 호출
→ SQL reservation_requests pending 생성
→ Cloud Tasks worker 처리
→ SQL transaction으로 예약 생성/수정/취소 확정
```

## 왜 필요한가

예약 오픈 직후 많은 고객이 동시에 예약 버튼을 누르면, 단순 요청 수보다 더 위험한 것은 같은 상품과 같은 방문 시간대에 대한 DB 락 경합입니다.

이번 구조는 역할을 나눕니다.

- Vercel Redis waiting room: Cloud Run과 Cloud SQL로 들어오는 순간 요청 수를 줄입니다.
- Cloud Run API: 예약 생성/수정/취소 요청을 접수하고 조회 가능한 `request_uuid`를 발급합니다.
- Cloud Tasks: 접수된 예약 변경 요청을 정해진 속도로 worker에 전달합니다.
- Cloud SQL transaction: 실제 재고, 방문 시간 정원, 중복 예약을 최종 검증합니다.

## 백엔드 변경 사항

### 새 DB 테이블

`reservation_requests`

주요 컬럼:

- `uuid`: 고객에게 반환하는 예약 요청 번호
- `user_id`, `user_uuid`: 요청한 고객
- `sale_date`: 예약 대상 판매 일자
- `action`: `create`, `update`, `cancel`
- `target_reservation_uuid`: 수정/취소 대상 예약 번호. 생성 요청에서는 빈 값
- `idempotency_key`: 같은 고객의 중복 요청 방지 키
- `status`: `pending`, `enqueued`, `processing`, `success`, `failed`, `enqueue_failed`
- `payload_json`: 원본 예약 생성/수정 요청
- `result_json`: 성공 시 생성/수정/취소된 예약 UUID 목록
- `error_message`: 실패 이유
- `task_name`: Cloud Tasks 작업 이름
- `attempts`: worker 처리 시도 횟수

제약:

- `(user_id, idempotency_key)`는 unique입니다.
- 같은 고객이 같은 key로 다시 요청하면 새 예약을 만들지 않고 기존 요청 상태를 반환합니다.

### 새 API

#### POST `/reservation-requests`

Vercel waiting room을 통과한 고객만 호출해야 하는 예약 생성 접수 API입니다. `reservation_requests.action=create`로 저장됩니다.

요청:

```json
{
  "sale_date": "2026-07-01",
  "idempotency_key": "client-generated-reservation-attempt-uuid",
  "items": [
    {
      "schedule_set_uuid": "schedule-set-uuid",
      "product_uuid": "product-uuid",
      "quantity": 1,
      "time_slot_uuid": "slot-uuid"
    }
  ]
}
```

응답:

```json
{
  "request_uuid": "reservation-request-uuid",
  "action": "create",
  "status": "enqueued",
  "sale_date": "2026-07-01",
  "target_reservation_uuid": "",
  "idempotency_key": "client-generated-reservation-attempt-uuid",
  "error_message": "",
  "reservations": [],
  "attempts": 0,
  "created_at": "2026-06-21T01:00:00Z",
  "updated_at": "2026-06-21T01:00:00Z",
  "finished_at": null
}
```

보안:

- 운영에서는 Vercel Function이 `X-Reservation-Gateway-Secret` 헤더를 붙입니다.
- 브라우저에는 이 secret을 절대 넣지 않습니다.
- 백엔드의 `RESERVATION_GATEWAY_SECRET`이 비어 있으면 검사를 건너뜁니다. 로컬 개발용입니다.

#### PATCH `/reservations/{reservation_uuid}`

예약 수정 API입니다. 더 이상 즉시 예약 row를 바꾸지 않고, `reservation_requests.action=update` 요청을 만든 뒤 worker가 처리합니다.

요청:

```json
{
  "idempotency_key": "client-generated-update-attempt-uuid",
  "quantity": 2,
  "time_slot_uuid": "new-slot-uuid"
}
```

응답은 `POST /reservation-requests`와 같은 요청 상태 객체이며, `action=update`, `target_reservation_uuid={reservation_uuid}`입니다.

정합성 규칙:

- 같은 예약에 대해 이미 `pending`, `enqueued`, `processing` 상태의 수정/취소 요청이 있으면 409를 반환합니다.
- worker 처리 시점에 예약 row, 상품 row, 방문 시간 row를 다시 lock하고 재고/정원/1인 제한을 재검증합니다.
- 성공하면 `reservations[0]`에 수정된 예약 정보가 담깁니다.

#### DELETE `/reservations/{reservation_uuid}`

예약 취소 API입니다. 더 이상 즉시 취소하지 않고, `reservation_requests.action=cancel` 요청을 만든 뒤 worker가 처리합니다.

요청 헤더:

```http
Idempotency-Key: client-generated-cancel-attempt-uuid
```

응답은 `POST /reservation-requests`와 같은 요청 상태 객체이며, `action=cancel`, `target_reservation_uuid={reservation_uuid}`입니다.

정합성 규칙:

- 같은 예약에 대해 이미 처리 대기 중인 수정/취소 요청이 있으면 409를 반환합니다.
- worker가 예약 row를 lock한 뒤 아직 `reserved` 상태인지 확인합니다.
- 성공하면 `reservations[0].status`는 `cancelled`입니다.

#### GET `/reservation-requests/{request_uuid}`

고객이 예약 요청의 처리 결과를 조회합니다.

프론트 polling 규칙:

- `pending`, `enqueued`, `processing`: 계속 대기 화면
- `success`: action에 따라 내 예약 생성/수정/취소 결과 반영
- `failed`: `error_message` 표시
- `enqueue_failed`: 접수 처리 실패 안내 및 재시도 유도

#### POST `/internal/reservation-worker`

Cloud Tasks가 호출하는 내부 처리 API입니다.

보안:

- 운영에서는 `X-Reservation-Worker-Secret`이 `RESERVATION_WORKER_SECRET`과 일치해야 합니다.
- 프론트엔드는 이 API를 호출하지 않습니다.

## 프론트엔드 변경 사항

### 기존 흐름

```text
브라우저
→ Vercel Rewrite
→ Cloud Run 예약 생성/수정/취소 API
→ 즉시 확정/실패 또는 기존 직접 처리
```

### 신규 흐름

```text
브라우저
→ Vercel Function
→ Redis waiting room 확인
→ Cloud Run 예약 생성/수정/취소 API
→ request_uuid 반환
→ 브라우저가 GET /reservation-requests/{request_uuid} polling
```

### 프론트에서 반드시 해야 할 일

- 예약 버튼 클릭 직후 버튼을 비활성화합니다.
- 생성/수정 시도마다 `idempotency_key`를 생성합니다.
- 취소 시도마다 `Idempotency-Key` 헤더 값을 생성합니다.
- 같은 생성/수정/취소 시도에서 네트워크 재시도나 새로고침 복구를 할 때는 같은 key를 재사용합니다.
- 고객이 완전히 새 시도를 시작하면 새 key를 만듭니다.
- waiting room 통과 전에는 Cloud Run 예약 생성/수정/취소 API를 호출하지 않습니다.
- gateway secret은 Vercel Function의 서버 환경변수로만 사용합니다.
- 브라우저 JS, localStorage, 정적 HTML에 gateway secret을 넣지 않습니다.

## Vercel Redis waiting room 권장 구조

판매 일자 오픈/마감 시 `wr:open:{sale_date}`를 실제로 갱신하는 절차는 `docs/rev_004.md`를 기준으로 합니다. rev_003은 예약 생성/수정/취소 요청이 waiting room을 통과한 뒤 Cloud Run/Cloud Tasks로 넘어가는 구조를 설명합니다.

Redis key 예시:

- `wr:open:{sale_date}`: 해당 날짜 예약 waiting room 활성 여부
- `wr:queue:{sale_date}`: 대기열 sorted set
- `wr:active:{sale_date}`: 현재 입장 허용된 사용자 set
- `wr:lease:{sale_date}:{user_uuid}`: 입장 허용 lease

권장 동작:

1. 고객이 예약 버튼을 누릅니다.
2. Vercel Function이 사용자 토큰을 확인합니다.
3. Redis에서 해당 날짜의 waiting room 상태를 확인합니다.
4. 아직 입장 불가이면 대기 순번 또는 재시도 시간을 반환합니다.
5. 입장 허용이면 짧은 TTL lease를 발급합니다.
6. lease가 있는 고객 요청만 Cloud Run 예약 생성/수정/취소 API로 전달합니다.
7. Cloud Run 호출 시 `Authorization` 헤더와 `X-Reservation-Gateway-Secret` 헤더를 함께 보냅니다.

권장 TTL:

- 입장 lease: 30-90초
- 예약 결과 polling: 1-2초 간격에서 시작해 3-5초로 완화
- 실패 또는 성공 후 waiting room active set에서 제거

## Vercel Web GUI 작업 순서

Vercel Dashboard에서 다음 순서로 확인합니다.

1. 프로젝트 선택

   - Vercel Dashboard에 접속합니다.
   - 프론트엔드 프로젝트 `reservation-io`를 선택합니다.

2. Redis/KV 연결 확인

   - 상단 또는 좌측 메뉴에서 `Storage`를 엽니다.
   - 현재 연결된 Redis/KV가 프로젝트에 연결되어 있는지 확인합니다.
   - 연결되어 있지 않다면 `Connect Store` 또는 `Create Database`에서 Redis 계열 저장소를 연결합니다.
   - 연결 후 자동으로 생성되는 Redis 환경변수가 Production/Preview 환경에 들어갔는지 확인합니다.

3. Environment Variables 추가

   `Settings` → `Environment Variables`에서 다음 값을 추가합니다.

   - `BACKEND_API_BASE_URL`: Vercel Function 서버 코드가 Cloud Run의 고객용 API를 호출할 때 쓰는 백엔드 origin. 예: `https://reservation-api-...run.app`
   - `RESERVATION_GATEWAY_SECRET`: Cloud Run의 같은 이름 Secret 값과 동일한 값
   - `WAITING_ROOM_ENABLED`: `true`
   - `WAITING_ROOM_MAX_ACTIVE`: 동시에 Cloud Run 예약 접수 API로 보낼 최대 고객 수
   - `WAITING_ROOM_LEASE_SECONDS`: 입장 허용 TTL, 예: `60`
   - `WAITING_ROOM_POLL_SECONDS`: 대기 화면 재조회 간격, 예: `2`

   주의:

   - `RESERVATION_GATEWAY_SECRET`은 `NEXT_PUBLIC_` 접두사를 붙이지 않습니다.
   - `NEXT_PUBLIC_` 접두사가 붙은 값은 브라우저에 노출될 수 있습니다.
   - `BACKEND_API_BASE_URL`은 Vercel 서버 함수 내부용 값입니다. 브라우저 공개 환경변수로 만들지 않습니다.
   - `BACKEND_API_BASE_URL`은 Cloud Tasks worker 호출 주소가 아닙니다. Cloud Tasks worker 주소는 Cloud Run 쪽 `RESERVATION_WORKER_URL`로만 관리합니다.
   - Vercel에는 `RESERVATION_WORKER_URL`을 둘 필요가 없습니다. 이 값은 Cloud Run 백엔드가 Cloud Tasks에 작업을 등록할 때만 사용합니다.

4. 예약 변경 API route를 Vercel Function으로 전환

   기존에 모든 API를 단순 Rewrite로 Cloud Run에 넘기고 있었다면, 예약 생성/수정/취소 경로는 예외로 둡니다.

   권장:

   - `/api/reservation-requests`는 Vercel Function이 처리합니다.
   - `/api/reservations/:reservation_uuid`의 `PATCH`, `DELETE`도 Vercel Function이 처리합니다.
   - 이 Function들이 Redis waiting room을 확인한 뒤 Cloud Run의 동일 경로를 호출합니다.
   - 나머지 조회 API는 기존 Rewrite를 유지할 수 있습니다.

5. Deployments에서 재배포

   - 환경변수를 저장한 뒤 Production 배포를 다시 실행합니다.
   - 배포 후 예약 버튼을 눌러 waiting room 상태, 예약 접수, 결과 polling이 순서대로 동작하는지 확인합니다.

## GCP/Cloud Run 설정

Cloud Run 환경변수:

- `RESERVATION_QUEUE_BACKEND=cloud_tasks`
- `CLOUD_TASKS_PROJECT_ID=reservation-io`
- `CLOUD_TASKS_LOCATION=asia-northeast3`
- `CLOUD_TASKS_QUEUE=reservation-requests`
- `RESERVATION_WORKER_URL=https://.../internal/reservation-worker`
- `CLOUD_TASKS_SERVICE_ACCOUNT_EMAIL=reservation-api-runner@reservation-io.iam.gserviceaccount.com`
- `CLOUD_TASKS_AUDIENCE`: OIDC를 쓸 때 worker URL 또는 Cloud Run audience

Cloud Run Secret:

- `RESERVATION_GATEWAY_SECRET`
- `RESERVATION_WORKER_SECRET`

Cloud Tasks queue:

- 이름: `reservation-requests`
- 리전: Cloud Run과 같은 `asia-northeast3` 권장
- dispatch rate: 처음에는 낮게 시작합니다. 예: 초당 10-30건
- max concurrent dispatches: 처음에는 낮게 시작합니다. 예: 5-20

운영자는 실제 예약 오픈 부하 테스트 후 이 값을 조정합니다.

## 정합성 보장 방식

1. Waiting room은 피크를 줄이지만 최종 정합성을 보장하지 않습니다.
2. Cloud Tasks는 같은 작업을 재시도할 수 있습니다.
3. 백엔드 worker는 `reservation_requests` 행을 lock합니다.
4. 이미 `success` 또는 `failed`인 요청은 다시 처리하지 않습니다.
5. 실제 예약 생성/수정/취소는 사용자, 일정, 상품, 시간대, 예약 행을 transaction 안에서 lock합니다.
6. 재고 부족, 시간대 마감, 이미 예약 있음, 수령 완료 후 재예약, 이미 취소된 예약 같은 검증은 worker에서 최종 판단합니다.
7. 수정/취소는 같은 예약에 대해 이미 처리 대기 중인 변경 요청이 있으면 새 요청을 받지 않습니다.
8. Cloud Tasks가 매우 빠르게 worker를 실행해 API 응답 전에 요청이 끝나도, API는 DB row를 다시 읽어 `success`/`failed` 상태를 `enqueued`로 되돌리지 않습니다.

## 테스트해야 할 케이스

- gateway secret 없이 `/reservation-requests` 호출 시 403
- 같은 idempotency key 두 번 호출 시 같은 `request_uuid` 반환
- worker를 같은 `request_uuid`로 두 번 호출해도 예약은 1건만 생성
- 재고 1개 상품에 2명이 요청하면 첫 요청만 success, 다음 요청은 failed
- 방문 시간 정원 1명 시간대에 2명이 요청하면 첫 요청만 success, 다음 요청은 failed
- 수정 요청은 `action=update` pending 요청을 만들고 worker 성공 후 예약 수량/방문 시간이 바뀜
- 취소 요청은 `action=cancel` pending 요청을 만들고 worker 성공 후 예약 상태가 `cancelled`가 됨
- 같은 예약에 대해 수정/취소 pending 요청이 있을 때 추가 수정/취소 요청은 409
- 취소된 예약을 다시 수정하거나 다시 취소하면 worker 결과가 failed
- `failed` 상태에서 프론트 polling이 멈추고 `error_message`를 표시
- `enqueue_failed` 상태에서 고객에게 다시 시도 안내
