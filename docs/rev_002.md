# rev_002 변경 명세

이번 변경은 방문 확인 수동 코드 충돌 방지, 과도한 요청 차단 책임 분리, 방문 확인증 API 응답 구체화, 재고/정원 검증 재확인을 다룹니다.

## 변경 요약

- 수동 방문 확인 코드 충돌 관리를 Firestore 기반으로 바꿨습니다.
- 운영 배포에서는 `OTP_MANUAL_CODE_REGISTRY_BACKEND=firestore`를 사용합니다.
- 로컬 개발에서는 기본값이 `memory`라 GCP 인증 없이 테스트할 수 있습니다.
- 백엔드는 IP 기반 요청 차단을 수행하지 않습니다.
- 과도한 요청 차단은 Vercel Rewrites + Vercel KV에서 담당합니다.
- 방문 확인증 QR API는 오늘 예약만 QR 토큰을 발급하고, 미래 예약만 있으면 안내 메시지를 반환합니다.
- Firestore 읽기/쓰기가 필요한 수동 코드는 별도 API에서 필요할 때만 발급합니다.
- 방문 확인증 토큰 항목에 예약 요약 정보를 함께 반환합니다.

## Firestore 수동 코드 충돌 방지

### 왜 필요한가

수동 코드는 기본 12자리이므로 충돌 가능성이 매우 낮지만 0은 아닙니다. 현장에서는 수동 코드가 고객을 찾는 키가 되므로, 같은 유효 시간 안에 서로 다른 예약이 같은 수동 코드를 갖지 않도록 보장해야 합니다.

### 저장 방식

Firestore collection:

- 기본값: `manual_otp_codes`
- 문서 ID: 수동 코드 문자열

문서 필드:

```json
{
  "code": "a1b2c3d4e5f6",
  "user_uuid": "user-uuid",
  "reservation_uuid": "reservation-uuid",
  "counter": 59320000,
  "nonce": 0,
  "issued_at": "Firestore Timestamp",
  "expires_at": "Firestore Timestamp"
}
```

### 충돌 처리

1. 백엔드는 기본 수동 코드인 `nonce=0` 코드를 계산합니다.
2. Firestore 문서 트랜잭션으로 해당 코드가 이미 유효하게 점유되어 있는지 확인합니다.
3. 문서가 없거나 `expires_at`이 지났으면 현재 예약으로 저장합니다.
4. 같은 예약이 이미 같은 코드를 점유하고 있으면 그대로 재사용합니다.
5. 다른 예약이 아직 유효하게 점유 중이면 충돌입니다.
6. 충돌 시 1초 대기 대신 `nonce=1`, `nonce=2`처럼 즉시 다른 후보 코드를 계산합니다.
7. 기본 최대 시도 횟수는 `OTP_MANUAL_CODE_MAX_ATTEMPTS=16`입니다.

1초 대기보다 nonce 재시도가 더 나은 이유:

- 기존 TOTP counter는 30초 단위라 1초를 기다려도 코드가 바뀌지 않을 수 있습니다.
- nonce 방식은 사용자 대기 없이 같은 30초 창 안에서 충돌 없는 코드를 만들 수 있습니다.
- QR 해시는 기존 알고리즘을 유지합니다.

### 관리자 스캔 처리

수동 코드는 QR 인식이 불가능해 관리자가 직접 입력해야 하는 상황에서만 발급합니다. 고객 화면이 QR을 표시하기 위해 `GET /users/me/visit-tokens`를 호출하는 것만으로는 Firestore를 읽거나 쓰지 않습니다.

관리자가 수동 코드를 입력하면 백엔드는 먼저 Firestore에서 수동 코드 문서를 조회합니다.

- 문서가 있고 `expires_at`이 지나지 않았으면 해당 `reservation_uuid`를 직접 조회합니다.
- 문서가 없거나 만료되었으면 기존 TOTP 검증 흐름으로 fallback합니다.
- QR 스캔은 기존처럼 예약별 TOTP 해시 검증을 사용합니다.

## 새 환경변수

```env
OTP_MANUAL_CODE_REGISTRY_BACKEND=firestore
OTP_MANUAL_CODE_COLLECTION=manual_otp_codes
OTP_MANUAL_CODE_MAX_ATTEMPTS=16
FIRESTORE_PROJECT_ID=reservation-io
FIRESTORE_DATABASE=(default)
```

로컬 개발 예시는 다음처럼 둘 수 있습니다.

```env
OTP_MANUAL_CODE_REGISTRY_BACKEND=memory
```

## 과도한 요청 차단 구조 변경

프론트엔드는 Vercel에 배포되어 있으므로, 과도한 버튼 클릭과 반복 호출은 Vercel Rewrites + Vercel KV에서 먼저 차단합니다.

백엔드 변경:

- 백엔드의 DB 기반 rate limit 미들웨어와 IP 밴 검사는 비활성화되었습니다.
- `ip_rate_limits`와 `ip_bans`는 운영 요청 차단에 사용하지 않습니다.
- 관리자 로그인 실패는 401만 반환하며 IP 차단을 만들지 않습니다.
- `DB_BASED_IP_BAN`, `ADMIN_LOGIN_FAIL_LIMIT`, `ANTI_MACRO_DURATION`, `ANTI_MACRO_RETENTION_SECONDS`는 더 이상 배포 환경변수로 사용하지 않습니다.
- `/admin/ip-bans` API는 호환용입니다. 목록은 빈 배열, 추가는 410, 삭제는 no-op 204입니다.

프론트엔드 작업:

- 예약하기, 예약 수정, 예약 취소, 방문 완료, 영업 마감 버튼은 요청 중 비활성화합니다.
- 같은 API 연속 호출은 Vercel KV에서 IP/세션/사용자 기준으로 제한합니다.
- Vercel 단에서 제한된 사용자는 프론트에서 안내 화면으로 보냅니다.
- 백엔드의 `/users/me/block-status`는 호환용이며 항상 `blocked=false`를 반환합니다.

## 방문 확인증 API 변경

### GET `/users/me/visit-tokens`

응답 형식이 배열에서 객체로 바뀌었습니다. 이 API는 QR 표시 전용이며 수동 코드를 발급하지 않습니다.

```json
{
  "tokens": [
    {
      "reservation_uuid": "reservation-uuid",
      "sale_date": "2026-07-01",
      "schedule_set_uuid": "schedule-set-uuid",
      "schedule_title": "1차 예약",
      "product_name": "상품명",
      "quantity": 1,
      "time_slot_label": "14:00",
      "qr_hash": "b6fc4c620b67d95f953a5c1c1230aaab",
      "expires_in_seconds": 18,
      "hash_window": "t-1,t,t+1"
    }
  ],
  "message": ""
}
```

오늘 예약이 없고 미래 예약만 있는 경우:

```json
{
  "tokens": [],
  "message": "방문 확인 코드는 예약 당일에만 발급됩니다."
}
```

오늘 발급 가능한 예약이 전혀 없는 경우:

```json
{
  "tokens": [],
  "message": "오늘 발급 가능한 방문 확인 코드가 없습니다."
}
```

프론트엔드 작업:

- QR 칸 위에 `schedule_title`, `product_name`, `quantity`, `time_slot_label`을 표시합니다.
- `tokens`가 비어 있으면 QR 영역 대신 `message`를 표시합니다.
- 방문 확인증 화면에 들어왔을 때만 이 API를 호출합니다.
- 이 API 응답에는 `manual_code`가 없습니다.

### POST `/users/me/visit-manual-code`

QR 인식이 안 되어 현장에서 수동 입력이 필요할 때만 호출합니다.

요청:

```json
{
  "reservation_uuid": "reservation-uuid"
}
```

응답:

```json
{
  "reservation_uuid": "reservation-uuid",
  "sale_date": "2026-07-01",
  "schedule_set_uuid": "schedule-set-uuid",
  "schedule_title": "1차 예약",
  "product_name": "상품명",
  "quantity": 1,
  "time_slot_label": "14:00",
  "manual_code": "a1b2c3d4e5f6",
  "expires_in_seconds": 18,
  "hash_window": "t-1,t,t+1"
}
```

프론트엔드 작업:

- 예약별 QR 영역에 `수동 코드 발급` 버튼을 둡니다.
- 화면 진입, QR 갱신, 타이머 갱신만으로 이 API를 자동 호출하지 않습니다.
- 발급 후 반환된 `manual_code`를 크게 표시하고, 관리자가 입력할 수 있도록 12자리를 읽기 좋게 보여줍니다.
- 실패 시 “예약 당일에만 발급됩니다”, “수동 코드 저장소를 사용할 수 없습니다” 등의 백엔드 메시지를 그대로 안내합니다.
- 관리자 QR 스캔은 `POST /admin/visits/scan`에 `token_type=qr`를 보냅니다.
- 관리자 수동 입력은 `POST /admin/visits/scan`에 `token_type=manual`을 보냅니다.
- `token_type=auto`는 호환용입니다. QR 스캔 기본값으로 쓰면 Firestore 조회가 먼저 발생할 수 있습니다.

중요:

- “메인 화면에 머무는 동안 계속 TOTP를 갱신하지 않기”는 프론트엔드의 업무입니다.
- 백엔드는 요청이 왔을 때만 토큰을 발급하며, 어떤 화면이 열려 있는지는 알 수 없습니다.

## GCP Web GUI 설정 가이드

아래 절차는 Google Cloud Console 기준입니다.

공식 참고 링크:

- [Firestore TTL 정책](https://docs.cloud.google.com/firestore/native/docs/ttl)
- [Firestore IAM 역할과 권한](https://docs.cloud.google.com/iam/docs/roles-permissions/firestore)
- [Firestore 서버 클라이언트 IAM 보안](https://docs.cloud.google.com/firestore/native/docs/security/iam)

### 1. Firestore 데이터베이스 만들기

1. Google Cloud Console에서 `reservation-io` 프로젝트를 선택합니다.
2. 왼쪽 메뉴 또는 검색창에서 `Firestore`를 엽니다.
3. `Databases` 또는 `데이터베이스` 화면으로 이동합니다.
4. `Create a Firestore database`를 누릅니다.
5. database ID는 기본값인 `(default)`를 사용합니다.
6. 모드는 `Native mode`를 선택합니다.
7. 위치는 가능하면 Cloud Run과 가까운 리전을 선택합니다.
8. 보안 규칙은 서버에서만 접근할 예정이면 제한적으로 둡니다.

참고: Google 공식 문서도 콘솔에서 Firestore database를 생성하고, ID와 모드/에디션을 선택하는 흐름을 안내합니다.

### 2. Cloud Run 실행 계정 권한 부여

Cloud Run 서비스 계정:

```text
reservation-api-runner@reservation-io.iam.gserviceaccount.com
```

권한:

```text
Cloud Datastore User
roles/datastore.user
```

GUI 절차:

1. Google Cloud Console에서 `IAM & Admin` > `IAM`으로 이동합니다.
2. `Grant access` 또는 `액세스 권한 부여`를 누릅니다.
3. Principal에 위 Cloud Run 서비스 계정을 입력합니다.
4. Role에서 `Cloud Datastore User`를 선택합니다.
5. 저장합니다.

Firestore는 IAM에서 Datastore 계열 권한 이름을 사용합니다.

### 3. TTL 설정

TTL은 백엔드 검증을 대체하지 않습니다. 백엔드는 항상 `expires_at`을 직접 확인합니다. TTL은 오래된 수동 코드 문서를 나중에 자동 삭제해 저장 공간을 줄이는 용도입니다.

GUI 절차:

1. Google Cloud Console에서 `Firestore`로 이동합니다.
2. `Time-to-live` 또는 `TTL` 설정 화면을 엽니다.
3. 새 TTL 정책을 만듭니다.
4. collection group은 `manual_otp_codes`로 둡니다.
5. timestamp field는 `expires_at`으로 둡니다.
6. 저장합니다.

Google 공식 TTL 문서도 TTL 정책은 Timestamp 필드를 기준으로 오래된 문서를 정리하는 기능이라고 설명합니다.

### 4. Cloud Build 환경변수 확인

`cloudbuild.yaml`에 다음 값이 들어가 있어야 합니다.

```yaml
_OTP_MANUAL_CODE_REGISTRY_BACKEND: firestore
_OTP_MANUAL_CODE_COLLECTION: manual_otp_codes
_OTP_MANUAL_CODE_MAX_ATTEMPTS: "16"
_FIRESTORE_PROJECT_ID: reservation-io
_FIRESTORE_DATABASE: "(default)"
```

## 재고/방문 정원 이상 케이스 검증

검증한 케이스:

- 시간대 정원은 10명인데 상품 재고가 1개인 경우, 첫 예약만 성공하고 두 번째 예약은 재고 부족으로 실패해야 합니다.
- 상품 재고는 충분하지만 시간대 정원이 1명인 경우, 첫 고객만 성공하고 두 번째 고객은 시간대 마감으로 실패해야 합니다.
- 한 번의 예약 요청 안에 같은 상품이 여러 줄로 중복되어 들어오더라도, 상품별 합산 수량이 1인 제한과 재고를 넘으면 실패해야 합니다.

백엔드 검증 순서:

- 예약 생성 시 상품 행을 잠그고 재고 예약 합계를 확인합니다.
- 시간대가 있으면 시간대 행을 잠그고 예약 고객 수를 확인합니다.
- 고객 수는 예약 행 수가 아니라 `distinct user_id` 기준입니다.
- 예약 수정 시에도 같은 재고/시간대 검증을 다시 수행합니다.
