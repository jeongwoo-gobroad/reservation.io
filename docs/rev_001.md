# rev_001 변경 명세

이 문서는 이번 변경으로 프론트엔드 구현자가 반영해야 할 API, 화면 동작, 예외 처리를 정리합니다.

## 핵심 변경 요약

- 초당 반복 요청이 일정 기준 이상이면 해당 IP를 차단합니다.
- IP 차단 목록에 차단 사유, 사용자 번호, 닉네임을 함께 보관합니다.
- 차단된 고객은 로그인 후 일반 메인 화면이 아니라 차단 안내 화면으로 이동해야 합니다.
- 차단 안내 문구는 관리자가 수정할 수 있습니다.
- 고객 상단바에 닉네임을 표시해야 합니다.
- 방문 완료 또는 노쇼 처리된 같은 고유 일정은 다시 예약할 수 없습니다.
- 고객은 내 예약에서 수량과 방문 시간을 수정할 수 있습니다.
- 프론트엔드는 버튼 반복 클릭을 먼저 막아 서버 차단이 발생하지 않도록 해야 합니다.

## IP 수집과 차단 원리

백엔드는 접속 IP를 `X-Forwarded-For` 헤더의 첫 번째 값에서 우선 수집합니다. Cloud Run, Vercel 같은 배포 환경에서는 실제 브라우저 요청이 중간 서비스를 거쳐 들어오기 때문에 이 헤더가 일반적으로 원래 접속 IP를 담습니다. 헤더가 없으면 서버가 직접 본 `request.client.host` 값을 사용합니다.

차단은 DB의 `ip_bans` 테이블로 처리합니다. 요청이 들어오면 예약, 방문 확인, 관리자 기능이 실행되기 전에 현재 IP가 활성 차단 목록에 있는지 확인합니다. 차단되어 있으면 `403`을 반환하고 실제 기능은 실행하지 않습니다.

## Rate Limit 정책

환경변수:

- `ANTI_MACRO_DURATION`: 1초 안에 허용할 요청 횟수 기준입니다.
- 기본값은 `10`입니다.
- `ANTI_MACRO_RETENTION_SECONDS`: 요청 창 기록을 보관할 시간입니다.
- 기본값은 `3600`초입니다.

서버 동작:

- 로그인된 요청만 자동 차단 카운트에 포함합니다.
- 카운트 기준은 `IP 주소 + 로그인 사용자 + API 경로 + 1초 시간창`입니다.
- 같은 집이나 같은 매장 Wi-Fi를 쓰더라도 서로 다른 로그인 사용자는 서로의 카운트에 섞이지 않습니다.
- 다른 API를 호출한 횟수도 서로 섞이지 않습니다.
- 같은 조합에서 1초 안에 `ANTI_MACRO_DURATION`회 이상 요청하면 `ip_bans`에 자동 등록합니다.
- 차단 사유는 예: `초당 동일 API 요청 10회 감지(차단 기준 10회, API POST /reservations)` 형태로 저장됩니다.
- 로그인 토큰이 있는 고객 요청이면 사용자 번호와 닉네임도 함께 저장합니다.
- 토큰이 없는 일반 익명 요청은 자동 차단 카운트에서 제외합니다.
- 관리자 로그인 실패 차단은 이 기능과 별도로 `ADMIN_LOGIN_FAIL_LIMIT` 기준을 사용합니다.
- 오래된 요청 창은 `ANTI_MACRO_RETENTION_SECONDS`보다 오래되면 삭제합니다. SQL DB에는 Redis 같은 자동 TTL이 없으므로, 백엔드가 요청 처리 중 오래된 창을 정리합니다.
- 자동 매크로 차단은 `IP + 로그인 사용자` 범위로 저장합니다. 같은 IP의 다른 로그인 사용자는 함께 차단되지 않습니다.
- 관리자가 IP 관리 화면에서 수동으로 등록하는 차단은 전체 IP 차단입니다.

Thread-safe / Race-condition-safe 처리:

- 서버 메모리 카운터가 아니라 DB 행을 기준으로 카운트합니다.
- `(ip_address, actor_key, route_key, window_started_at)`가 unique입니다.
- 같은 사용자, 같은 IP, 같은 API, 같은 1초 창의 카운트 행을 `SELECT ... FOR UPDATE`로 잠그고 증가시킵니다.
- Cloud Run 인스턴스가 여러 개 떠도 같은 카운트 행을 순서대로 갱신합니다.
- 차단 목록도 같은 IP 행을 잠근 뒤 활성화합니다.
- 최초 요청에서 같은 카운트 행이 동시에 생성되는 경우를 대비해 unique 충돌 시 다시 조회합니다.

## 차단 응답 형식

차단된 요청은 `403`을 반환합니다.

```json
{
  "detail": {
    "code": "ip_banned",
    "message": "현재 접속이 제한되어 있습니다. 매장 관리자에게 문의해 주세요.",
    "ip_address": "203.0.113.10",
    "actor_key": "user:7f3b7e0a-9f3f-4fa7-94c7-0f49a623e990",
    "user_uuid": "7f3b7e0a-9f3f-4fa7-94c7-0f49a623e990",
    "nickname": "고객닉네임",
    "reason": "초당 요청 10회 감지(차단 기준 10회)"
  }
}
```

프론트엔드 공통 처리:

- `detail.code === "ip_banned"`이면 즉시 차단 전용 화면으로 이동합니다.
- 차단 화면에서는 예약 목록, QR, 예약 버튼을 보여주지 않습니다.
- 차단 사유는 관리자용 정보이므로 고객 화면에는 너무 자세히 노출하지 않는 것을 권장합니다.

## 새 API: 내 차단 상태 확인

### GET `/users/me/block-status`

로그인 후 고객이 차단 상태인지 확인합니다. 이 API는 차단된 IP에서도 호출할 수 있습니다.

인증:

- 사용자 Bearer 토큰 필요

응답:

```json
{
  "blocked": true,
  "ip_address": "203.0.113.10",
  "actor_key": "user:7f3b7e0a-9f3f-4fa7-94c7-0f49a623e990",
  "user_uuid": "7f3b7e0a-9f3f-4fa7-94c7-0f49a623e990",
  "nickname": "고객닉네임",
  "reason": "초당 요청 10회 감지(차단 기준 10회)",
  "message_markdown": "현재 접속이 제한되어 있습니다. 매장 관리자에게 문의해 주세요."
}
```

프론트엔드 흐름:

1. 카카오 로그인 완료 후 토큰을 저장합니다.
2. `GET /users/me/block-status`를 먼저 호출합니다.
3. `blocked=true`이면 차단 전용 화면으로 이동합니다.
4. `blocked=false`이면 기존 메인 화면으로 이동합니다.

## 새 공개 설정: 차단 안내 문구

### GET `/settings/blocked_user_message_markdown`

고객 차단 화면에서 보여줄 문구입니다.

응답:

```json
{
  "key": "blocked_user_message_markdown",
  "value": "현재 접속이 제한되어 있습니다. 매장 관리자에게 문의해 주세요."
}
```

관리자 수정:

- `GET /admin/settings/blocked_user_message_markdown`
- `PUT /admin/settings/blocked_user_message_markdown`

프론트엔드 작업:

- 관리자 문구 관리 화면에 “접속 제한 안내문” 항목을 추가합니다.
- Markdown 미리보기를 지원합니다.
- 고객 차단 화면은 이 문구를 Markdown으로 렌더링합니다.

## IP 관리 변경

### GET `/admin/ip-bans`

기존 응답에 `user_uuid`, `nickname`이 추가됩니다.

```json
[
  {
    "id": 1,
    "ip_address": "203.0.113.10",
    "actor_key": "user:7f3b7e0a-9f3f-4fa7-94c7-0f49a623e990",
    "user_uuid": "7f3b7e0a-9f3f-4fa7-94c7-0f49a623e990",
    "nickname": "고객닉네임",
    "reason": "초당 요청 10회 감지(차단 기준 10회)",
    "active": true,
    "created_at": "2026-06-20T01:00:00Z",
    "updated_at": "2026-06-20T01:00:00Z"
  }
]
```

### POST `/admin/ip-bans`

수동 차단 또는 수정 시 `user_uuid`, `nickname`을 보낼 수 있습니다.

```json
{
  "ip_address": "203.0.113.10",
  "actor_key": "",
  "user_uuid": "7f3b7e0a-9f3f-4fa7-94c7-0f49a623e990",
  "nickname": "고객닉네임",
  "reason": "수동 차단",
  "active": true
}
```

### DELETE `/admin/ip-bans/{ip_address}`

차단 해제는 기존처럼 수동 삭제 API를 사용합니다.

쿼리:

- `actor_key`: 선택값입니다. 주면 해당 사용자 범위 차단만 해제합니다. 생략하면 해당 IP의 모든 차단을 해제합니다.

프론트엔드 작업:

- IP 관리 테이블에 닉네임, 사용자 번호, 차단 사유를 표시합니다.
- 닉네임과 IP로 빠르게 찾을 수 있는 검색 UI를 권장합니다.
- 해제 버튼은 반드시 확인 창을 거칩니다.

## 프론트엔드 1차 Rate Limit 방어

서버 차단은 마지막 방어선입니다. 고객이 실수로 여러 번 누르는 상황은 프론트에서 먼저 막아야 합니다.

권장 구현:

- 예약하기, 예약 수정, 예약 취소, 방문 완료, 영업 마감 같은 버튼은 클릭 직후 비활성화합니다.
- 요청이 끝나기 전 같은 버튼을 다시 누르지 못하게 합니다.
- 같은 API를 짧은 시간에 반복 호출하는 화면은 300-500ms debounce 또는 throttle을 둡니다.
- QR 갱신은 `expires_in_seconds` 기준으로 정해진 타이머에서만 호출합니다.
- 목록 새로고침 버튼은 연속 클릭 방지를 둡니다.
- API 공통 클라이언트에서 `403 ip_banned`를 감지해 차단 화면으로 이동합니다.

## 상단바 닉네임 표시

사용 API:

- `GET /users/me`

응답의 `nickname`을 고객 화면 상단바에 간단히 표시합니다.

표시 규칙:

- 닉네임이 있으면 `닉네임` 또는 `닉네임님` 형태로 표시합니다.
- 닉네임이 비어 있으면 닉네임 설정 화면으로 보내거나 “닉네임 미설정”처럼 짧게 표시합니다.
- 디버그용 사용자 번호는 운영 화면에 표시하지 않습니다.

## 예약 재예약 제한

백엔드 변경:

- 같은 사용자와 같은 `schedule_set_uuid`에 대해 `visited` 또는 `no_show` 상태 예약이 있으면 새 예약을 거부합니다.
- `cancelled` 상태는 예외입니다. 취소 후 재예약은 가능합니다.
- 현재 예약 중인 같은 날짜 예약은 기존 규칙대로 중복 예약을 막습니다.

오류 예시:

```json
{
  "detail": "[1차 예약] 일정은 이미 수령 완료 또는 노쇼 처리되어 다시 예약할 수 없습니다."
}
```

프론트엔드 작업:

- 예약 실패 시 백엔드 `detail` 메시지를 사용자에게 그대로 보여줍니다.
- 방문 완료된 일정이 다시 예약 가능 목록에 보이더라도 최종 예약 버튼에서 실패할 수 있으므로, 가능하면 고객의 과거 예약 상태를 함께 고려해 버튼을 비활성화합니다.

## 새 API: 예약 수정

### PATCH `/reservations/{reservation_uuid}`

고객이 내 예약에서 수량 또는 방문 시간을 수정합니다.

인증:

- 사용자 Bearer 토큰 필요

요청:

```json
{
  "quantity": 2,
  "time_slot_uuid": "time-slot-uuid"
}
```

부분 수정:

- 수량만 바꿀 수 있습니다.
- 방문 시간만 바꿀 수 있습니다.
- 둘 다 함께 바꿀 수 있습니다.

응답:

```json
{
  "uuid": "reservation-uuid",
  "sale_date": "2026-07-01",
  "schedule_set_uuid": "schedule-set-uuid",
  "schedule_title": "1차 예약",
  "product_uuid": "product-uuid",
  "product_name": "상품명",
  "quantity": 2,
  "time_slot_uuid": "time-slot-uuid",
  "time_slot_label": "14:30",
  "status": "reserved",
  "reserved_at": "2026-06-20T01:00:00Z"
}
```

백엔드 검증:

- 현재 로그인한 사용자의 예약인지 확인합니다.
- 예약 상태가 `reserved`일 때만 수정합니다.
- 상품 재고를 넘지 않는지 확인합니다.
- 상품별 1인당 최대 구매 개수를 넘지 않는지 확인합니다.
- 상품 그룹의 구매 제한을 넘지 않는지 확인합니다.
- 방문 시간 정원이 남아 있는지 확인합니다.

프론트엔드 작업:

- 내 예약 카드에 “예약 수정” 버튼을 추가합니다.
- 수정 화면에는 현재 수량과 현재 방문 시간을 기본값으로 넣습니다.
- 수량 선택 UI는 1부터 상품별 `per_user_limit`까지 보여줍니다.
- 방문 시간 선택 UI는 같은 일정의 `time_slots`를 실제 시간 라벨로 보여줍니다.
- 저장 중에는 버튼을 비활성화합니다.
- 성공하면 내 예약 목록을 다시 불러옵니다.
- 실패하면 백엔드 메시지를 눈에 띄게 보여줍니다.

## 시간 표시

기존 규칙 유지:

- 예약 카드 본문에는 `Seoul, KR` 같은 장소처럼 보이는 표현을 반복하지 않습니다.
- 화면 맨 아래 footer에만 `시간 표시 기준: Seoul, KR`을 둡니다.
- 예약 일시는 사용자가 이해할 수 있는 로컬 시간 문자열로 표시합니다.
- 방문 시간은 `14:00`처럼 실제 시간만 보여줍니다.

## 관리자 화면 반영 목록

관리자 메인:

- 마감되지 않은 지난 영업일을 계속 표시합니다.
- 영업 마감 시 노쇼 처리 안내와 확인 창을 보여줍니다.

IP 관리:

- 닉네임, 사용자 번호, 차단 사유 칼럼을 추가합니다.
- 차단 해제 버튼을 둡니다.

문구 관리:

- 접속 제한 안내문 항목을 추가합니다.

일정 관리:

- 상품 입력에 전체 재고와 1인당 최대 구매 제한을 모두 노출합니다.
- 상품 그룹 구매 제한도 명확히 보여줍니다.

방문 확인:

- 방문 완료된 예약은 같은 고유 일정에서 다시 예약할 수 없음을 운영자에게 안내할 수 있어야 합니다.

이번 변경에는 DB 칼럼과 새 테이블이 포함되어 있습니다. Cloud Run 배포 후 마이그레이션 Job을 실행해야 합니다.

관련 환경변수:

- `ANTI_MACRO_DURATION=10`
- `ANTI_MACRO_RETENTION_SECONDS=3600`
- `ADMIN_LOGIN_FAIL_LIMIT=5`

관련 DB 변경:

- `ip_bans.user_uuid`
- `ip_bans.nickname`
- `ip_bans.actor_key`
- `ip_bans` unique 기준: `(ip_address, actor_key)`
- `ip_rate_limits`
