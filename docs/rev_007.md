# rev_007: 예약 요청 정리 Job과 운영 설정 가이드

작성일: 2026-06-22  
대상: 백엔드 Cloud Run, Cloud Run Job, Cloud Scheduler, Vercel 환경변수

이 문서는 `docs/rev_006.md` 이후 추가된 변경사항과, Google Cloud Console 및 Vercel Web GUI에서 운영자가 해야 할 일을 설명합니다.

## 1. 이번 변경 요약

### 예약 요청 임시 행 정리

`reservation_requests`는 예약 생성/수정/취소를 처리하기 위한 작업표입니다. 장기 보존 장부가 아니므로, 24시간이 지난 행은 상태와 상관없이 삭제하도록 cleanup Job을 추가했습니다.

삭제 기준:

```text
reservation_requests.created_at < 현재 UTC 시각 - 24시간
```

삭제 대상 상태:

```text
success
failed
enqueue_failed
pending
enqueued
processing
```

즉, 지금 구현은 “24시간 이상 지난 모든 예약 요청 행 삭제”입니다.

### 새 실행 명령

Cloud Run Job은 아래 명령을 실행합니다.

```text
python -m reservation_api.maintenance cleanup-reservation-requests
```

실행이 끝나면 로그에 삭제 건수와 cutoff 시각이 남습니다.

예:

```text
cleanup_reservation_requests deleted=123 cutoff=2026-06-21T19:00:00+00:00 configured_gmt9_hour=4
```

### 새 환경변수

요청하신 이름:

```text
CLEANUP_GMT+9_HOUR=4
```

의미:

```text
한국 시각 기준 매일 몇 시에 cleanup을 실행할지 나타냅니다.
4이면 매일 새벽 4시입니다.
```

호환용 이름:

```text
CLEANUP_GMT_PLUS_9_HOUR=4
```

주의:

Cloud Run 문서는 환경변수를 key/value로 설정한다고 설명하고, `.env` 예시에서도 일반 셸 변수명보다 넓은 이름을 보여줍니다. 다만 `+` 문자는 배포 도구나 UI에서 제한될 수 있으므로, 백엔드는 `CLEANUP_GMT+9_HOUR`를 우선 읽고 `CLEANUP_GMT_PLUS_9_HOUR`도 함께 지원합니다.

## 2. 코드 변경 내역

추가:

- `reservation_api/maintenance.py`
- `alembic/versions/20260622_0011_align_model_indexes.py`

수정:

- `reservation_api/config.py`
- `.env.example`
- `cloudbuild.yaml`
- `docs/system_0622.md`
- `docs/gcp-cloudrun-manual.md`

핵심 함수:

```python
cleanup_reservation_requests(db)
```

역할:

1. 현재 UTC 시각을 구합니다.
2. 24시간 전 cutoff를 계산합니다.
3. `created_at < cutoff`인 `reservation_requests` 행을 삭제합니다.
4. commit합니다.
5. 삭제 건수를 반환합니다.

cleanup 기능 자체는 DB 컬럼 변경을 요구하지 않습니다. 다만 전체 검증 과정에서 Alembic head와 SQLAlchemy model의 인덱스 정의 차이를 발견했으므로, 인덱스 정합성을 맞추는 `20260622_0011_align_model_indexes.py` 마이그레이션을 함께 추가했습니다.

## 3. Cloud Build 변경

`cloudbuild.yaml`에 cleanup용 Cloud Run Job 배포 단계가 추가되었습니다.

Job 이름:

```text
reservation-api-cleanup-reservation-requests
```

배포 설정:

```text
command: python
args: -m reservation_api.maintenance cleanup-reservation-requests
```

필요한 secret:

```text
DATABASE_URL
```

cleanup Job은 DB에 직접 접속해 오래된 `reservation_requests` 행을 삭제합니다. 예약 API를 호출하지 않으므로 `RESERVATION_GATEWAY_SECRET`은 cleanup Job 자체에는 필요하지 않습니다.

## 4. GCP Web GUI에서 해야 할 일

### 4.1 Cloud Build로 새 백엔드 배포

1. Google Cloud Console에 접속합니다.
2. 프로젝트 `reservation-io`를 선택합니다.
3. `Cloud Build`로 이동합니다.
4. 기존 GitHub 트리거 또는 수동 빌드 방식으로 백엔드를 배포합니다.
5. 빌드가 성공하면 Cloud Run 서비스와 함께 cleanup Job도 배포됩니다.

확인 위치:

1. `Cloud Run`으로 이동합니다.
2. 왼쪽 메뉴에서 `Jobs`를 선택합니다.
3. `reservation-api-cleanup-reservation-requests`가 있는지 확인합니다.

### 4.2 cleanup Job 수동 실행 테스트

1. `Cloud Run` > `Jobs`로 이동합니다.
2. `reservation-api-cleanup-reservation-requests`를 클릭합니다.
3. 상단의 `Execute` 버튼을 누릅니다.
4. 실행이 끝날 때까지 기다립니다.
5. `Executions` 또는 `Logs`에서 아래 형태의 로그를 확인합니다.

```text
cleanup_reservation_requests deleted=...
```

Google Cloud 공식 문서 기준으로 Cloud Run Job은 요청을 계속 받는 서비스가 아니라, 작업을 실행하고 종료되는 컨테이너 작업입니다. 실행 기록과 로그는 Cloud Run Job execution과 Cloud Logging에서 확인합니다.

### 4.3 매일 새벽 4시 자동 실행 설정

Cloud Run Job은 스스로 매일 실행되지 않습니다. Cloud Scheduler가 정해진 시간에 Job을 깨워야 합니다.

가장 쉬운 GUI 절차:

1. `Cloud Run`으로 이동합니다.
2. 왼쪽 메뉴에서 `Jobs`를 선택합니다.
3. `reservation-api-cleanup-reservation-requests`를 클릭합니다.
4. `Triggers` 탭을 엽니다.
5. `Add Scheduler Trigger`를 누릅니다.
6. Cloud Scheduler API 활성화 안내가 나오면 `Enable API`를 누릅니다.
7. Scheduler 이름을 입력합니다.

권장 이름:

```text
reservation-requests-cleanup-daily
```

스케줄:

```text
0 4 * * *
```

시간대:

```text
Asia/Seoul
```

의미:

```text
매일 한국 시각 새벽 4시 실행
```

인증:

- Cloud Scheduler가 Cloud Run Job을 실행할 수 있는 서비스 계정을 선택합니다.
- 해당 서비스 계정에는 Cloud Run Job 실행 권한이 필요합니다.

권장 서비스 계정:

```text
reservation-cleanup-scheduler@reservation-io.iam.gserviceaccount.com
```

권장 역할:

```text
Cloud Run Invoker
```

Google Cloud 공식 문서 기준으로 Cloud Run Job 실행에는 Cloud Run Invoker 또는 Cloud Run Developer 권한이 필요합니다. 운영 자동 실행에는 최소 권한인 Cloud Run Invoker를 권장합니다.

### 4.4 Scheduler 서비스 계정 만들기

아직 없다면 다음 절차를 따릅니다.

1. `IAM & Admin`으로 이동합니다.
2. `Service Accounts`를 엽니다.
3. `Create service account`를 누릅니다.
4. 이름을 입력합니다.

예:

```text
reservation-cleanup-scheduler
```

5. 생성 후 `IAM` 메뉴로 이동합니다.
6. `Grant access`를 누릅니다.
7. principal에 아래 값을 입력합니다.

```text
reservation-cleanup-scheduler@reservation-io.iam.gserviceaccount.com
```

8. role은 `Cloud Run Invoker`를 부여합니다.

보안을 더 좁히려면 project 전체가 아니라 해당 Cloud Run Job 리소스에만 권한을 주는 방식을 선택할 수 있습니다.

### 4.5 Scheduler 동작 확인

1. `Cloud Scheduler`로 이동합니다.
2. `reservation-requests-cleanup-daily`를 찾습니다.
3. `Force run` 또는 `Run now`를 눌러 테스트합니다.
4. `Cloud Run` > `Jobs` > `reservation-api-cleanup-reservation-requests`에서 새 execution이 생기는지 확인합니다.
5. Logs에서 `cleanup_reservation_requests` 로그가 찍히는지 확인합니다.

## 5. Vercel Web GUI에서 해야 할 일

이번 cleanup Job은 Vercel에서 실행되지 않습니다. 따라서 cleanup 자체를 위해 Vercel에 새 환경변수를 추가할 필요는 없습니다.

다만 기존 보안 구조 때문에 아래 값은 계속 유지해야 합니다.

### 5.1 Vercel에 유지해야 하는 서버 환경변수

```text
RESERVATION_GATEWAY_SECRET
BACKEND_API_BASE_URL
API_REWRITE_ORIGIN
WAITING_ROOM_ENABLED
WAITING_ROOM_MAX_ACTIVE
WAITING_ROOM_LEASE_SECONDS
WAITING_ROOM_POLL_SECONDS
REDIS_URL 또는 UPSTASH_REDIS_REST_URL/UPSTASH_REDIS_REST_TOKEN
```

`RESERVATION_GATEWAY_SECRET`은 Vercel 서버 함수가 Cloud Run에 예약 생성/수정/취소, 판매일 open/close 요청을 전달할 때 붙이는 비밀값입니다.

주의:

```text
RESERVATION_GATEWAY_SECRET에 NEXT_PUBLIC_ 접두사를 붙이지 마십시오.
```

브라우저 JavaScript에 노출되면 안 됩니다.

### 5.2 Gateway secret을 어디에 넣어야 하는가

답:

```text
예, 넣어야 합니다.
```

정확히는 두 곳에 같은 값을 넣어야 합니다.

1. GCP Secret Manager

```text
reservation-gateway-secret
```

Cloud Run 백엔드에서는 이 secret이 `RESERVATION_GATEWAY_SECRET` 환경변수로 주입됩니다.

2. Vercel Environment Variables

```text
RESERVATION_GATEWAY_SECRET
```

Vercel route handler가 Cloud Run 호출 시 `X-Reservation-Gateway-Secret` 헤더로 보냅니다.

cleanup Job 자체는 gateway secret을 쓰지 않습니다. 하지만 Cloud Run API 서비스는 예약 변경 endpoint를 보호하기 위해 `RESERVATION_GATEWAY_SECRET`이 필요하고, 운영 환경에서는 이 값이 비어 있으면 앱 시작을 막습니다.

### 5.3 Vercel에서 추가 작업이 필요한 경우

이번 cleanup 변경만으로는 Vercel 코드 변경이 필요 없습니다.

다만 다음 경우에는 프론트/Vercel 작업이 필요합니다.

- 백엔드 `ADMIN_LOGIN_GATEWAY_REQUIRED=true`로 전환할 경우
- 관리자 로그인도 Vercel route handler를 통해 호출하고 싶을 경우

그때는 Vercel에 `/api/admin/login` 서버 route handler를 만들고, Cloud Run `/admin/login` 호출에 `X-Reservation-Gateway-Secret`을 붙여야 합니다.

현재 프론트가 일반 `/api/backend/admin/login` rewrite를 사용한다면 `ADMIN_LOGIN_GATEWAY_REQUIRED=false`를 유지하십시오.

## 6. 향후 stale 처리 가능성

현재는 단순 정책입니다.

```text
created_at 기준 24시간 지난 모든 reservation_requests 삭제
```

논리적으로 예약 피크 작업이 24시간 이상 `pending`, `enqueued`, `processing`에 남아 있을 이유는 거의 없습니다. 그런 행은 정상 대기가 아니라 장애 흔적입니다.

향후 운영 관측이 필요해지면 아래 정책으로 바꿀 수 있습니다.

1. `pending`, `enqueued`, `processing`이 일정 시간 이상 남아 있으면 바로 삭제하지 않음
2. 먼저 `failed` 또는 `stale_failed` 같은 상태로 전환
3. `error_message`에 “장시간 처리되지 않아 만료됨” 기록
4. 일정 시간 뒤 삭제

현재는 요청대로 24시간이 지난 모든 행을 삭제합니다.

```text
python -m reservation_api.maintenance cleanup-reservation-requests
```

예상 출력:

```text

```

Cloud Run Job 검증:

1. Cloud Run > Jobs에서 수동 `Execute`
2. Logs에서 `cleanup_reservation_requests deleted=` 확인
3. DB에서 24시간 지난 `reservation_requests` 행이 줄어드는지 확인

Scheduler 검증:

1. Cloud Scheduler에서 수동 실행
2. Cloud Run Job execution 생성 확인
3. Logs 확인
